# Workflow — как дирижёр решает, кто делает работу

## Кто дирижёр

**Главная сессия Claude — дирижёр.** Она делает большинство работы **сама** — этот проект уже
построен и работает, ему нужна поддержка и аккуратное развитие, а не симуляция целой команды на
каждый чих. Специалисты-агенты вызываются точечно, для конкретной задачи, и **возвращают результат
дирижёру**, а не друг другу — цепочки агент→агент дороги и теряют контекст.

При старте дирижёр читает: `CLAUDE.md` → `.claude/rules/index.md` → этот файл → `.claude/rules/team.md`.

## Базовое правило

**Дирижёр делает задачу сам**, если это не одно из:

| Ситуация | Кого вызвать |
|----------|--------------|
| Файл/сервис разросся (напр. >300 строк), нужна структурная декомпозиция/выбор технологии, или Sonar/CodeQL/линтер сигналят code smell/нарушение SOLID | `architect` |
| Задача затрагивает auth/инвайты/admin/email/персональные данные, или нужен триаж security-алерта | `security-engineer` |
| Нужны тесты (unit/integration/e2e) или проверка UI в браузере | `tester` |
| CI/CD, Dockerfiles, docker-compose, версии GitHub Actions | `devops` |
| Изменилось пользовательское поведение — нужен апдейт README/CHANGELOG | `technical-writer` |
| Нужна read-only проверка сборки/линта/тестов без засорения контекста | `build-validator` |
| Нужен снимок устаревших/уязвимых пакетов и файлов >300 строк (начало `/maintain` или разово) | `repo-scout` |
| Достаточно крупная backend/frontend-подзадача, которую стоит изолировать (напр. параллельная работа) | `server-developer` / `ui-developer` |
| Нужен независимый взгляд на дифф перед PR (свежий контекст) | `architect` (ревью диффа — тоже архитектурная зона) |

Всё остальное — мелкие правки, точечные фиксы, ответы на вопросы, рутинные апдейты
зависимостей — дирижёр делает напрямую.

Таблица выше — типичные случаи, не исчерпывающий список условий и не запрет вызывать агента вне
её строк. **Дирижёр вправе вызвать любого специалиста по собственному усмотрению** — не только
в перечисленных ситуациях — в любой момент, когда сам видит риск, сомневается в решении или считает,
что взгляд конкретной роли будет полезен. Например: `architect` — если видит архитектурный риск
раньше порога >300 строк или до того, как Sonar/CodeQL что-то отметят; `security-engineer` — если
сомневается в чувствительности места, формально не попавшего в таблицу; `tester` — если хочет
независимую проверку сценария, не дожидаясь явного «нужны тесты». Это право, а не обязанность —
экономность (см. «Когда НЕ вызывать агента» ниже) остаётся в силе: не плодить агентов под разовую
мелочь, использовать усмотрение для реальных случаев, а не как повод спавнить чаще.

## Примеры

**Тривиальная правка** (опечатка, переименование, мелкий фикс): дирижёр делает сам →
`build-validator` перед коммитом → готово.

**Баг:** воспроизвести/локализовать (дирижёр) → починить (дирижёр, или `server-developer`/
`ui-developer`, если объёмно) → `tester` — тест, фиксирующий регресс → `build-validator` — зелёный
билд → `technical-writer` — запись в `CHANGELOG.md` (`Fixed`), если поведение видно пользователю.

**Крупная фича/структурный рефакторинг:** `architect` — план и декомпозиция → реализация
(дирижёр или `server-developer`/`ui-developer` по подзадачам) → `tester` → `build-validator` →
`security-engineer`, если затронуто чувствительное → `technical-writer`, если видимое поведение
изменилось.

**Плановая поддержка (регулярно, см. `/maintain`):** обновление зависимостей
(скилл `dependency-freshness`) → `security-engineer` — триаж алертов → `architect` — сканирование
на рефакторинг и на устаревшие технологические решения (кандидаты — отдельным GitHub Issue с меткой
`tech-radar` на согласование, не auto-adopt) → PR → независимая ревизия диффа (`architect` со
свежим контекстом, либо явный запрос code-review) → `security-engineer` при необходимости.

## Definition of Done (общая для задачи)

1. Код реализован и соответствует плану (если привлекался `architect`).
2. Билд **зелёный** (0 ошибок), предупреждения просмотрены.
3. Тесты добавлены/обновлены и проходят; для видимых UI-изменений — проверено в браузере.
4. `CHANGELOG.md`/README обновлены, если поведение изменилось для пользователя.
5. Чувствительные части (если затронуты) согласованы с `security-engineer`.

## Скептицизм к результатам агентов

Агентский self-report «готово»/«тесты зелёные»/«билд проходит» — это заявление, не доказательство.
Субагент может остановиться раньше, чем прогнал весь чек-лист (упасть по лимиту, решить, что
«и так сойдёт», или ошибиться в диагнозе). Дирижёр **не подписывает работу под агента**: перед тем,
как коммитить/мержить/пушить результат чужой (суб)агентской работы — прогони проверку сам или через
`build-validator`, а не полагайся на текст отчёта.

Это не значит «сверять каждый шаг агента, пока он работает» — процесс агента не нужно
контролировать построчно, вмешательство именно в чужую работу без повода не приветствуется. Значит
это ровно одно: **вывод** (код, чинёный баг, вердикт «зелено») перепроверяется независимо, прежде
чем на него полагается следующий шаг.

Прецеденты из практики (не гипотетические, ради которых стоит держать это правило):
- Фронтенд-агент отчитался об успехе, но сам не успел дойти до `npm run build` (упал по лимиту
  трат раньше) — в его же новом тесте была ошибка типов, которую поймал только реальный прогон
  сборки, не его самоотчёт.
- Первая попытка починить провал SonarCloud по дублированию (test-mock дублирование) была основана
  на правдоподобной, но неверной догадке — сдвинула метрику на 0.1 п.п. вместо ожидаемого. Настоящий
  источник дублирования нашёлся только через независимый прогон `jscpd`, а не через повторную
  догадку.

## Дисциплина бюджета сессии

- Контекст текущих моделей (порядка 1M) — не узкое место (см. `index.md`); дробление задач служит
  параллельности и изоляции шумного вывода, не экономии токенов.
- **Но это не отменяет дисциплину — она просто переезжает.** `CLAUDE.md` в корне репозитория
  читается **каждой** сессией целиком — держи его компактным (принципы, конвенции, ссылки), а не
  местом для детальных инструкций «на все случаи»: плоский файл с полусотней конкретных правил —
  тот самый убер-промпт, только замаскированный под инфраструктуру, и правила в нём начинают
  противоречить друг другу (три правила про тесты в одном файле → агент рандомно выбирает, какое
  применить). Детальные, ситуативные инструкции — в `.claude/agents/*` (грузится только когда
  вызвана роль) и `.claude/skills/*` (грузится только когда применим скилл), не в корневой файл.
- Делегируй объёмные/шумные операции субагентам (`build-validator` вместо дампа компилятора).
- Приоритет — **завершить начатую** задачу; новые запросы, не блокирующие текущую работу, можно
  зафиксировать GitHub Issue и вернуться к ним позже.
- Если виден риск нехватки бюджета — останови, сообщи пользователю текущее состояние и что
  осталось, не молчи о незавершённости.

### Когда НЕ вызывать агента (экономность)

- **Тривиальную/среднюю задачу дирижёр делает сам.** Спавн агента стоит дорого: он стартует
  «с нуля» и заново выводит контекст. Вызывай специалиста только ради (а) реальной экспертизы роли
  (архитектура, безопасность), (б) изоляции шумного вывода, или (в) достаточно крупной автономной
  подзадачи.
- Не выстраивай цепочки агент→агент — возвращай результат дирижёру, он решает следующий шаг.
- Не плоди агентов под разовую мелочь.
