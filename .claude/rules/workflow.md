# Workflow — как дирижёр решает, кто делает работу

## Кто дирижёр

**Главная сессия Claude — дирижёр.** Она делает большинство работы **сама** — этот проект уже
построен и работает, ему нужна поддержка и аккуратное развитие, а не симуляция целой команды на
каждый чих. Специалисты-агенты вызываются точечно, для конкретной задачи, и **возвращают результат
дирижёру**, а не друг другу — цепочки агент→агент дороги и теряют контекст.

При старте дирижёр читает: `CLAUDE.md` → `.claude/rules/index.md` → этот файл → `.claude/rules/team.md`.

## Базовое правило

**Дирижёр делает задачу сам**, если это не одно из:

| Ситуация | Кого вызвать |
|----------|--------------|
| Файл/сервис разросся (напр. >300 строк), нужна структурная декомпозиция/выбор технологии, или Sonar/CodeQL/линтер сигналят code smell/нарушение SOLID | `architect` |
| Задача затрагивает auth/инвайты/admin/email/персональные данные, или нужен триаж security-алерта | `security-engineer` |
| Нужны тесты (unit/integration/e2e) или проверка UI в браузере | `tester` |
| CI/CD, Dockerfiles, docker-compose, версии GitHub Actions | `devops` |
| Изменилось пользовательское поведение — нужен апдейт README/CHANGELOG | `technical-writer` |
| Нужна read-only проверка сборки/линта/тестов без засорения контекста | `build-validator` |
| Достаточно крупная backend/frontend-подзадача, которую стоит изолировать (напр. параллельная работа) | `server-developer` / `ui-developer` |
| Нужен независимый взгляд на дифф перед PR (свежий контекст) | `architect` (ревью диффа — тоже архитектурная зона) |

Всё остальное — мелкие правки, точечные фиксы, ответы на вопросы, рутинные апдейты
зависимостей — дирижёр делает напрямую.

## Примеры

**Тривиальная правка** (опечатка, переименование, мелкий фикс): дирижёр делает сам →
`build-validator` перед коммитом → готово.

**Баг:** воспроизвести/локализовать (дирижёр) → починить (дирижёр, или `server-developer`/
`ui-developer`, если объёмно) → `tester` — тест, фиксирующий регресс → `build-validator` — зелёный
билд → `technical-writer` — запись в `CHANGELOG.md` (`Fixed`), если поведение видно пользователю.

**Крупная фича/структурный рефакторинг:** `architect` — план и декомпозиция → реализация
(дирижёр или `server-developer`/`ui-developer` по подзадачам) → `tester` → `build-validator` →
`security-engineer`, если затронуто чувствительное → `technical-writer`, если видимое поведение
изменилось.

**Плановая поддержка (регулярно, см. `/maintain`):** обновление зависимостей
(скилл `dependency-freshness`) → `security-engineer` — триаж алертов → `architect` — сканирование
на рефакторинг и на устаревшие технологические решения (кандидаты — в `backlog/ideas.md` на
согласование, не auto-adopt) → PR → независимая ревизия диффа (`architect` со свежим контекстом,
либо явный запрос code-review) → `security-engineer` при необходимости.

## Definition of Done (общая для задачи)

1. Код реализован и соответствует плану (если привлекался `architect`).
2. Билд **зелёный** (0 ошибок), предупреждения просмотрены.
3. Тесты добавлены/обновлены и проходят; для видимых UI-изменений — проверено в браузере.
4. `CHANGELOG.md`/README обновлены, если поведение изменилось для пользователя.
5. Чувствительные части (если затронуты) согласованы с `security-engineer`.

## Дисциплина бюджета сессии

- Контекст ограничен (200K). Большие задачи **дробятся** до старта (см. `index.md`).
- Делегируй объёмные/шумные операции субагентам (`build-validator` вместо дампа компилятора).
- Приоритет — **завершить начатую** задачу; новые запросы, не блокирующие текущую работу, можно
  зафиксировать (в GitHub Issue или `backlog/ideas.md`) и вернуться к ним позже.
- Если виден риск нехватки бюджета — останови, сообщи пользователю текущее состояние и что
  осталось, не молчи о незавершённости.

### Когда НЕ вызывать агента (экономность)

- **Тривиальную/среднюю задачу дирижёр делает сам.** Спавн агента стоит дорого: он стартует
  «с нуля» и заново выводит контекст. Вызывай специалиста только ради (а) реальной экспертизы роли
  (архитектура, безопасность), (б) изоляции шумного вывода, или (в) достаточно крупной автономной
  подзадачи.
- Не выстраивай цепочки агент→агент — возвращай результат дирижёру, он решает следующий шаг.
- Не плоди агентов под разовую мелочь.
