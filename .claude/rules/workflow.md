# Workflow — жизненный цикл задачи и ворота

> Этот файл — **процесс**. Он веб-нейтрален и копируется в любой проект без изменений.
> Специфика конкретного проекта (стек, команды сборки) — в `CLAUDE.md`.

## Кто дирижёр

**Главная сессия Claude — дирижёр (conductor).** Субагенты её не заменяют: они вызываются
для ограниченной задачи и **возвращают результат дирижёру**, а не друг другу. Глубокие цепочки
агент→агент дороги и теряют контекст — избегаем их.

При старте дирижёр читает: `CLAUDE.md` → `.claude/rules/index.md` → этот файл → `.claude/rules/team.md`.

Субординация = **задокументированный пайплайн + RACI** (см. `team.md`), а не runtime-иерархия.
«Главный в своём вопросе» означает: в своей зоне роль принимает решение, и её выход — вход
для следующих ворот.

## Жизненный цикл (ворота)

Не каждая задача проходит все ворота. Дирижёр выбирает минимально необходимый путь
(ценность «Простота» + «Экономность»). Тривиальная правка может идти Build → Quality напрямую.

| # | Ворота | Ответственная роль | Артефакт-передача (выход) |
|---|--------|--------------------|---------------------------|
| 1 | **Intake** — что и зачем | `business-analyst` | критерии приёмки, согласованный объём |
| 2 | **Backlog** — декомпозиция | `scrum-master` | задачи в `roadmap.md` / `tasks.md` |
| 3 | **Design** — как делать | `architect` (+ `designer` для UI) | план реализации, выбор технологий, разбиение |
| 4 | **Build** — реализация | `server-developer` / `ui-developer` | код + локальная проверка |
| 5 | **Test** — проверка | `tester` (unit/integ) + `manual-tester` (e2e) | тесты зелёные, отчёт о дефектах |
| 6 | **Quality gate** — годность | `build-validator` (+ `security-engineer` для чувствительного) | зелёный билд/линт, отчёт безопасности |
| 7 | **Docs** — документация | `technical-writer` (+ `translator` для локализаций) | актуальные доки/локализации |
| 8 | **Release** — выпуск | `devops` / `release-engineer` | релиз, обновлённый changelog/версия |
| 9 | **Meta** — обслуживание | `manager` | актуальные агенты/правила/скилы/доки |

## Таблица триггеров «событие → кого звать»

| Событие | Кого вызвать |
|---------|--------------|
| Неясны требования пользователя | `business-analyst` |
| Новая «хотелка» / надо ничего не забыть | `scrum-master` (занести в backlog) |
| Нужна архитектура / разбить большую задачу / выбрать технологию | `architect` |
| Вопрос внешнего вида / UX-потока / стиля | `designer` |
| Писать/менять серверный код | `server-developer` |
| Писать/менять UI-код | `ui-developer` |
| Нужны unit/integration тесты | `tester` |
| Проверить в браузере / e2e | `manual-tester` |
| Проверить билд/линт без замусоривания контекста | `build-validator` |
| Чувствительные данные, auth, платежи, загрузки | `security-engineer` |
| Лицензии пакетов / правовые вопросы | `lawyer` |
| Документация продукта / README / API | `technical-writer` |
| Локализация / перевод | `translator` |
| CI/CD, инфраструктура, деплой | `devops` |
| Готовность к релизу, анализ упавшего CI | `release-engineer` |
| Устарели агенты/правила/доки; бюджет сессии | `manager` |
| Вопрос «как у нас устроено X» | `qa` |

## Примеры прохода (как дирижёр выбирает путь)

Дирижёр выбирает **минимально необходимый** путь, а не все ворота подряд.

**А. Тривиальная правка** (опечатка, переименование, правка строки):
дирижёр делает сам → `build-validator` (Quality) → готово. Агентов не зовём (экономия).

**Б. Исправление бага:**
воспроизвести/локализовать (дирижёр или `qa`) → `tester` пишет падающий тест →
`server-developer`/`ui-developer` чинит → `build-validator` + `tester` зелёные →
`technical-writer` правит changelog (`Fixed`) → `scrum-master` закрывает.

**В. Новая фича** (полный путь):
`business-analyst` (критерии приёмки) → `scrum-master` (декомпозиция в backlog) →
`architect` (план, разбиение, точки риска) [+ `designer` если есть UI] →
`server-developer`/`ui-developer` (Build) → `tester` + `manual-tester` (Test) →
`build-validator` + `security-engineer` для чувствительного (Quality) →
`technical-writer` (Docs) → `devops`/`release-engineer` (Release) →
`scrum-master` переносит в `completed/non-released.md`.

> Правило: если сомневаешься, нужен ли агент — см. «Когда НЕ вызывать агента» ниже.
> Чем мельче задача, тем короче путь.

## Definition of Done (общая для задачи)

Задача считается выполненной, когда:
1. Код реализован и соответствует плану архитектора (если он привлекался).
2. Билд **зелёный** (0 ошибок), варнинги просмотрены — см. `index.md` «Дисциплина билдов».
3. Тесты добавлены/обновлены и проходят.
4. Документация и локализации актуальны (если затронуты).
5. Задача перенесена `scrum-master`'ом в `backlog/completed/non-released.md`.

## Дисциплина бюджета сессии

- Контекст ограничен (200K). Большие задачи **дробятся** до старта (см. `index.md`).
- Делегируй объёмные/шумные операции субагентам (`build-validator` вместо дампа компилятора).
- Приоритет — **завершить начатую** задачу, новые хотелки уходят в backlog (ценность «Надёжность»).
- Если виден риск нехватки бюджета — останови, зафиксируй состояние в `tasks.md`, оставь
  рекомендации для следующей сессии (роль `manager` помогает это оценить).

### Когда НЕ вызывать агента (экономность)
- **Тривиальную задачу дирижёр делает сам.** Спавн агента стоит дорого: он стартует «с нуля» и
  заново выводит контекст. Вызывай специалиста только ради (а) реальной экспертизы роли,
  (б) изоляции шумного вывода, или (в) ограниченной автономной подзадачи.
- Не выстраивай цепочки агент→агент — возвращай результат дирижёру, он решает следующий шаг.
- Не плоди агентов под разовую мелочь; для повторяющейся рутины — дешёвый (haiku) агент.
