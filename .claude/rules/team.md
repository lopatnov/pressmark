# Team — роли и когда их вызывать

> Описывает **кто за что отвечает**. Процесс — в `workflow.md`. Должностные инструкции —
> в `.claude/agents/*`.

## Роли

Восемь ролей, каждая закрывает реальную, регулярно нужную зону работы над этим проектом —
никаких «стабов на будущее»:

| Роль | Модель | Зона ответственности |
|------|--------|----------------------|
| [`architect`](../agents/architect.md) | **opus** | Архитектура, декомпозиция крупных задач, «тяжёлый» рефакторинг (файлы >300 строк), выбор технологий |
| [`server-developer`](../agents/server-developer.md) | sonnet | Изолированные backend-подзадачи, достаточно большие для отдельного контекста |
| [`ui-developer`](../agents/ui-developer.md) | sonnet | Изолированные frontend-подзадачи, достаточно большие для отдельного контекста |
| [`tester`](../agents/tester.md) | sonnet | Тесты всех уровней (unit → e2e в браузере через скилл `run`) |
| [`security-engineer`](../agents/security-engineer.md) | sonnet | Auth/данные/секреты, триаж security-алертов (Dependabot/CodeQL/Socket) |
| [`devops`](../agents/devops.md) | sonnet | CI/CD, Docker, базовые образы, GitHub Actions |
| [`technical-writer`](../agents/technical-writer.md) | sonnet | README, CHANGELOG, документация продукта |
| [`build-validator`](../agents/build-validator.md) | haiku | Read-only прогон сборки/линта/тестов, структурированный вердикт |

Большинство мелких и средних задач **дирижёр (главная сессия) делает сам**, без спавна агента —
см. «Когда НЕ вызывать агента» в `workflow.md`. Роли выше — это специалисты для (а) реальной
экспертизы (архитектура, безопасность), (б) изоляции шумного вывода (`build-validator`), или
(в) достаточно крупной автономной подзадачи, оправдывающей стоимость нового контекста.

Новая роль нужна, только когда одной из восьми зон **регулярно и объёмно** не хватает — тогда
копируй `_TEMPLATE.md`. Не плоди роли под гипотетическое будущее.

## Кто главный в своей зоне

- **Структура/архитектура** → `architect`. Его решение по структуре и выбору технологий — финальное.
- **Безопасность** → `security-engineer`. Может заблокировать мерж до устранения серьёзного риска.
- **CI/CD и инфраструктура** → `devops`.
- **Тестирование** → `tester`.
- Во всём остальном решение принимает дирижёр (главная сессия), при необходимости — сверяясь
  с пользователем напрямую.

## Эскалация

- Архитектурный вопрос/конфликт (сложность, связность, выбор технологии) → `architect`.
- Риск безопасности → `security-engineer`.
- Неясность требований пользователя → вопрос пользователю напрямую (нет отдельной роли-посредника
  между пользователем и командой — задачи ставятся через GitHub Issues/PR или напрямую в диалоге).

## Политика инструментов (`tools:`)

Реальные имена Claude Code (не выдуманные): `Bash, Read, Glob, Grep, Edit, Write, Task,
TodoWrite, WebFetch, WebSearch`.

- **Стандартный набор** (большинство ролей): все перечисленные.
- **`build-validator`**: только `Bash, Read, Glob, Grep` — read-only + запуск проверок, без записи.
- **`tester`**: наследует все инструменты, включая браузерные MCP, если они доступны в сессии —
  для e2e-проверки через скилл `run`.

> Имя файла агента **обязано** совпадать с полем `name:` во frontmatter.
