# /maintain — плановая поддержка проекта

Формализует то, что дирижёр и так делает при запросе «поддержи проект», в повторяемый чек-лист —
чтобы качество поддержки не зависело от того, вспомнили ли в этот раз про конкретный шаг.

Если `$ARGUMENTS` указывает конкретный пункт — выполни только его. Иначе — все по порядку.
Каждый пункт — это отдельная ветка/PR (не смешивай обновление зависимостей с рефакторингом в
одном PR, их проще ревьюить и откатывать по отдельности).

## 0. Слить готовые Dependabot PR

**Перед** ручным обновлением зависимостей — проверь, нет ли уже открытых Dependabot PR, и слей
готовые: зелёный CI, тот же major (patch/minor bump), без конфликтов с `main`. Это не задваивает
работу шага 1 и не создаёт merge-конфликт между Dependabot-веткой и твоим собственным bump'ом того
же пакета.
- Список открытых Dependabot PR и их CI-статус — дирижёр смотрит **сам** через встроенные
  GitHub-инструменты сессии (`gh`/Dependabot API недоступны субагентам в этом окружении —
  см. `agents/repo-scout.md`, «Важное ограничение окружения»). Не делегируй этот шаг haiku-агенту.
- Merge-метод — тот же, что уже используется в истории репозитория (обычный merge commit через
  `merge_pull_request`, не squash — сверься с `git log --merges` при сомнении).
- PR с major bump'ом, красным CI или конфликтами — не сливай вслепую, оставь на шаг 1/2 (major —
  кандидат на `architect`, см. `dependency-freshness` skill).

Только после этого шага переходи к пункту 1 — там уже нет риска чинить то, что можно было просто
принять как есть.

## 1. Обновление зависимостей

Вызови [`repo-scout`](../agents/repo-scout.md) (haiku, read-only) — он одним проходом соберёт
устаревшие пакеты (backend/frontend), известные уязвимости из локальных сканеров и файлы >300
строк (пригодится и шагу 3). Возьми его список устаревших пакетов как отправную точку и следуй
чек-листу скилла [`dependency-freshness`](../skills/dependency-freshness/SKILL.md): backend
(NuGet), frontend (npm), .NET SDK, React major — отдельно от рутинных minor/patch. Тот же скилл
покрывает Docker-образы и версии GitHub Actions (разделы «Docker-образы»/«GitHub Actions») —
`repo-scout` их не собирает (не пакетный менеджер), эту часть чек-листа выполняет `devops`.

## 2. Security-алерты

Входные данные — список уязвимостей из отчёта `repo-scout` (шаг 1) плюс то, что не смогли слить
вслепую на шаге 0 (major-bump Dependabot PR почти всегда закрывают security-алерт — их описание
называет CVE/GHSA напрямую). Для каждой находки:
- Чинится обновлением версии/`overrides` — почини сразу здесь же (или в рамках шага 1, если это
  тот же PR обновления зависимостей).
- Не чинится тривиально (нужна структурная миграция) — заведи задачу для `architect`, не откладывай
  молча.
- Оценена как неприменимая/некритичная — задокументируй explicit обоснование (в PR-описании и/или
  `CHANGELOG.md`), а не просто проигнорируй. Пример подхода — история решений по
  `react-router-dom` RSC-CSRF и `@hono/node-server` в этом репозитории.

Роль: `security-engineer`.

## 3. Анализ на рефакторинг

Отправная точка — список файлов >300 строк из отчёта `repo-scout` (шаг 1), но это **сигнал, не
приговор**: количество строк — самый дешёвый и надёжный способ автоматически привлечь внимание
`architect`, не сама архитектурная проблема. Файл может быть длинным законно (сгенерированный код,
цельный enum) или коротким, но всё равно нарушать SOLID/содержать дублирование — `repo-scout` не
судит об этом, только считает строки. `architect` проверяет каждый файл из списка **и** ищет
смешение ответственностей/дублирование/нарушение SOLID/сигналы SonarCloud/CodeQL независимо от
размера (см. «Владение качеством кода» в `agents/architect.md`) — устоявшийся стиль `CLAUDE.md`
(партиал-классы по под-доменам backend, page+hook frontend) как ориентир. Не рефактори по инерции
то, что уже соответствует стилю.

Роль: `architect` — он же и выполняет «тяжёлый» рефакторинг, если он найден. Любой найденный по
пути реальный баг (не косметика) — тоже чинит здесь, а не откладывает отдельной задачей.

Сразу за рефакторингом — **не отдельным проходом позже**: покрой изменённое/исправленное тестами
нужного уровня (unit на новую логику, регресс-тест на каждый найденный и исправленный баг). Роль:
`tester`. Рефакторинг без теста, фиксирующего исправленное поведение, не считается завершённым.

## 4. Верификация

Перед тем как переходить к PR — прогон `build-validator`: сборка/линт/тесты backend и frontend,
формат. Не полагайся на самоотчёт роли, которая писала код (в т.ч. `architect`/`server-developer`/
`ui-developer`) — `build-validator` даёт независимую проверку тем же набором команд, что и CI.
Красный вердикт — возврат на шаг 3, не в PR.

## 5. Технологический радар

Проверь, не появилось ли более подходящих решений для существующих ключевых зависимостей/паттернов
(например: новая мажорная версия фреймворка, которая решает известную боль; библиотека, заменяющая
самописный код). **Не внедряй автоматически.** Каждую находку — отдельным GitHub Issue с меткой
`tech-radar` (что, зачем, какая цена перехода — в теле issue) на согласование с пользователем, не
файлом в репозитории.

## 6. Changelog

Если в шагах 1–3 что-то изменило видимое пользователю поведение (исправленный баг, закрытая
уязвимость, изменившийся API-контракт) — запись в `CHANGELOG.md` (`Unreleased`, секция
`Fixed`/`Security`/`Changed` по Keep a Changelog). Роль: `technical-writer`. Обновление
зависимостей само по себе без видимого эффекта — не требует записи; баг, найденный и исправленный
попутно в шаге 3 — требует.

## 7. PR, ревью сторонних ИИ-инструментов и наш собственный финальный ревью

Открой PR (или несколько — по одному на пункт 1–3, если правки в этом проходе получились разного
масштаба). Дальше — два разных ревью, оба обязательны, в этом порядке:

1. **Сторонние автоматические ревьюеры** (CodeRabbit, Socket, SonarCloud, CodeQL и т.п.) —
   дождись их прогона на PR и обработай замечания по стандартному протоколу подписки на
   PR-активность (см. системный промпт сессии): почини реальные находки, ответь на спорные,
   игнорируй дубликаты/шум.
2. **Наш собственный финальный код-ревью — только после этого.** Сторонние ИИ-инструменты не
   гарантируют полноты (у них нет контекста истории решений этого прохода, конвенций `CLAUDE.md`,
   что уже сознательно принято как риск) — за качество финальной проверки отвечаем мы, не
   перекладывай это на них. Получи независимый взгляд на дифф: вызови `architect` (или явно
   попроси ревью) с полным контекстом изменений и историей решений по этому проходу, чтобы он
   смотрел на дифф свежим взглядом, а не как соавтор. Рубрика — не изобретай заново: критерии уже
   есть в `agents/architect.md` («Владение качеством кода» — SOLID/дублирование/паттерны;
   «Static-analysis сигналы» — как трактовать Bug/Vulnerability/Code Smell/Duplication независимо
   от того, упал ли формально gate). **Всё найденное на этом ревью — почини сразу в рамках этого
   же прохода**, не откладывай отдельной задачей и не считай проход завершённым, пока список
   находок не пуст или не задокументирован как осознанно принятый (тот же принцип, что и для
   security-алертов в шаге 2).

## 8. Security-ревью (по необходимости)

Если проход затронул auth/инвайты/admin/email/персональные данные — дополнительный явный проход
`security-engineer` по этим местам, а не только триаж алертов из шага 2.

## Периодичность

Настроен реальный периодический запуск: Routine `trig_01UTHresmf26KejBiiNnvToH` («Pressmark
/maintain (bi-weekly)»), раз в 2 недели (1 и 15 число месяца, 6:00 UTC), с
`create_new_session_on_fire: true` (эта сессия эфемерна, не переживёт недели между запусками —
каждый firing стартует новую сессию в окружении). Заводить второй такой Routine не нужно; если
периодичность нужно поменять — `update_trigger`, не новый `create_trigger`.

Если настраиваешь заново (напр. Routine удалили) — спроси пользователя перед тем, как заводить
автоматический периодический запуск, который сам открывает PR без надзора.

## Definition of Done

Открытые Dependabot PR проверены и готовые слиты **до** начала ручного обновления (шаг 0),
зависимости сверены с `dependency-freshness` (не только «зелёный `npm install`»), открытые
security-алерты триажены (почищены или задокументированы как принятый риск), явных кандидатов на
рефакторинг/code smell нет либо они обработаны и покрыты тестами (`tester`), `build-validator`
подтвердил зелёный билд независимо от автора правок, видимые пользователю изменения — в
`CHANGELOG.md` (`technical-writer`), находки технологического радара — в GitHub Issues (метка
`tech-radar`), PR открыт, замечания сторонних ИИ-ревьюеров (CodeRabbit/Socket/SonarCloud/CodeQL)
обработаны, и **сверх этого** проведён наш собственный финальный ревью диффа (шаг 7, пункт 2) —
всё найденное на нём почищено или явно принято как риск, не оставлено «как есть» в расчёте на то,
что сторонние инструменты уже всё поймали.
