# /maintain — плановая поддержка проекта

Формализует то, что дирижёр и так делает при запросе «поддержи проект», в повторяемый чек-лист —
чтобы качество поддержки не зависело от того, вспомнили ли в этот раз про конкретный шаг.

Если `$ARGUMENTS` указывает конкретный пункт — выполни только его. Иначе — все по порядку.
Каждый пункт — это отдельная ветка/PR (не смешивай обновление зависимостей с рефакторингом в
одном PR, их проще ревьюить и откатывать по отдельности).

## 1. Обновление зависимостей

Следуй чек-листу скилла [`dependency-freshness`](../skills/dependency-freshness/SKILL.md):
backend (NuGet), frontend (npm), .NET SDK, React major — отдельно от рутинных minor/patch.
Плюс образы Docker и версии GitHub Actions (зона `devops`, тоже часть «зависимостей» проекта —
не только NuGet/npm).

## 2. Security-алерты

Провери открытые алерты репозитория (Dependabot/`npm audit`/CodeQL/Socket). Для каждого:
- Чинится обновлением версии/`overrides` — почини сразу здесь же (или в рамках шага 1, если это
  тот же PR обновления зависимостей).
- Не чинится тривиально (нужна структурная миграция) — заведи задачу для `architect`, не откладывай
  молча.
- Оценена как неприменимая/некритичная — задокументируй explicit обоснование (в PR-описании и/или
  здесь, в `backlog/`), а не просто проигнорируй. Пример подхода — история решений по
  `react-router-dom` RSC-CSRF и `@hono/node-server` в этом репозитории.

Роль: `security-engineer`.

## 3. Анализ на рефакторинг

Найди файлы/сервисы, разросшиеся за пределы устоявшегося стиля (`CLAUDE.md` — партиал-классы по
под-доменам backend, page+hook frontend; ориентир — файлы **>300 строк** или смешение
ответственностей). Не рефактори по инерции то, что уже соответствует стилю.

Роль: `architect` — он же и выполняет «тяжёлый» рефакторинг, если он найден.

## 4. Технологический радар

Проверь, не появилось ли более подходящих решений для существующих ключевых зависимостей/паттернов
(например: новая мажорная версия фреймворка, которая решает известную боль; библиотека, заменяющая
самописный код). **Не внедряй автоматически.** Каждую находку — короткой записью (что, зачем,
какая цена перехода) в [`backlog/ideas.md`](../backlog/ideas.md) на согласование с пользователем.

## 5. PR и независимая ревизия

Открой PR (или несколько — по одному на пункт 1–3, если правки в этом проходе получились разного
масштаба). Перед тем как считать проход завершённым — получи независимый взгляд на дифф: вызови
`architect` (или явно попроси ревью) с полным контекстом изменений и историей решений по этому
проходу, чтобы он смотрел на дифф свежим взглядом, а не как соавтор.

## 6. Security-ревью (по необходимости)

Если проход затронул auth/инвайты/admin/email/персональные данные — дополнительный явный проход
`security-engineer` по этим местам, а не только триаж алертов из шага 2.

## Периодичность

Эта команда рассчитана на регулярный (напр. раз в 1–4 недели) запуск, а не только на разовый
вызов пользователем. Если нужно настроить реальный периодический запуск — это делается через
Routine/cron окружения Claude Code (`create_trigger`), а не хранится в этом файле; спроси
пользователя перед тем, как заводить автоматический периодический запуск, который сам открывает
PR без надзора.

## Definition of Done

Зависимости сверены с `dependency-freshness` (не только «зелёный `npm install`»), открытые
security-алерты триажены (почищены или задокументированы как принятый риск), явных кандидатов на
рефакторинг >300 строк нет либо они обработаны, находки технологического радара — в
`backlog/ideas.md`, PR открыт и получил независимую ревизию диффа.
