# Testing — плейбук тестирования

*Как* тестировать. Конкретные команды (тест-раннер, запуск приложения, покрытие) — в `CLAUDE.md`,
здесь только стратегия.

## Когда применять
- Реализована/изменена логика.
- Нужно решить, каким уровнем тестов покрывать изменение.
- Перед мержем — подтвердить, что фича работает.

## Когда НЕ применять
- Тривиальная правка без поведения (опечатка, переименование) — достаточно `build-validator`.

## Пирамида тестов (снизу вверх — дешевле к дороже)
1. **Unit / component**. Быстрые, изолированные, их большинство. Можно писать **до** кода (TDD)
   как спецификацию.
2. **Integration**. Несколько модулей вместе (напр. gRPC-сервис против тестовой БД).
3. **End-to-end / браузер**. Немного, только критичные пользовательские потоки — открой приложение
   через скилл `run` и проверь вживую, не полагайся только на unit-тесты для визуальных/
   интерактивных изменений.

Все три уровня — зона роли `tester`. Правило экономности: покрывай нужным **минимальным** уровнем,
не гоняй e2e там, где хватает unit.

## Процедура
1. Из задачи выдели проверяемые сценарии, включая граничные/ошибки.
2. Выбери уровень(и) по пирамиде. Для новой логики — сначала падающий тест (TDD), затем код.
3. Прогони тесты; для UI — дополнительно проверь в браузере критичный путь.
4. Зелёный билд подтверждает `build-validator` (не дампи вывод в основной контекст).
5. Найденные дефекты — воспроизводимо описать и передать автору кода.

## Признаки хорошего теста
- Проверяет поведение, а не реализацию; имя описывает сценарий.
- Детерминирован (без флака), независим от других тестов, быстрый на своём уровне.
- Один тест — одна причина падения.

## Эскалация
- Тест требует слишком сложного метода / статический анализ просит снизить сложность → к
  `architect` (уточнить корректность архитектуры), а не «подгонять» тест.

## Definition of Done
Сценарии покрыты нужным уровнем тестов, тесты детерминированы и проходят, билд зелёный, найденные
дефекты переданы.
