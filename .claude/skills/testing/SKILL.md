# Testing — плейбук тестирования

Веб-нейтральный плейбук: *как* тестировать. Конкретные команды (тест-раннер, запуск приложения,
покрытие) живут в `CLAUDE.md` — здесь только стратегия и распределение ролей.

## Когда применять
- Реализована/изменена логика → ворота Test в `rules/workflow.md`.
- Нужно решить, каким уровнем тестов покрывать изменение.
- Перед воротами Quality/Release — подтвердить, что фича работает.

## Когда НЕ применять
- Тривиальная правка без поведения (опечатка, переименование) — достаточно `build-validator`.

## Пирамида тестов (снизу вверх — дешевле к дороже)
1. **Unit / component** → роль `tester`. Быстрые, изолированные, их большинство. Можно писать
   **до** кода (TDD) как спецификацию.
2. **Integration** → `tester` или `manual-tester` в зависимости от того, нужен ли реальный браузер.
3. **End-to-end / браузер** → роль `manual-tester` (Playwright / Chrome MCP). Немного, только
   критичные пользовательские потоки — они самые дорогие.

Правило экономности: покрывай нужным **минимальным** уровнем. Не гоняй e2e там, где хватает unit.

## Процедура
1. Из критериев приёмки (`business-analyst`) выдели проверяемые сценарии, включая граничные/ошибки.
2. Выбери уровень(и) по пирамиде. Для новой логики — сначала падающий тест (TDD), затем код.
3. `tester` пишет/гоняет unit/component; `manual-tester` — сквозные потоки в браузере.
4. Прогон и зелёный билд подтверждает `build-validator` (не дампи вывод в основной контекст).
5. Дефекты — воспроизводимо описать и передать авторам кода + `scrum-master` (как задачи).

## Признаки хорошего теста
- Проверяет поведение, а не реализацию; имя описывает сценарий.
- Детерминирован (без флака), независим от других тестов, быстрый на своём уровне.
- Один тест — одна причина падения.

## Эскалация
- Тест требует слишком сложного метода / Sonar просит снизить сложность → к `architect`
  (уточнить корректность архитектуры), а не «подгонять» тест.

## Definition of Done
Критерии приёмки покрыты нужным уровнем тестов, тесты детерминированы и проходят, билд зелёный,
найденные дефекты переданы. Соответствует Definition of Done в `rules/workflow.md`.
